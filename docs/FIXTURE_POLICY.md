# Fixture Policy

This document defines how test fixtures are created, reviewed, stored, and maintained in this repository.

---

## Purpose

Fixtures are the controlled inputs that tests are executed against. The quality of fixtures determines the quality of evidence. A test that runs on a poorly-understood fixture produces meaningless evidence — even if the test itself is well-written.

---

## Definitions

| Term | Definition |
|------|-----------|
| **fixture** | A static file or data structure used as controlled test input |
| **real-file fixture** | A fixture derived from or equivalent to real source material |
| **synthetic fixture** | A fixture constructed from scratch for a specific test case |
| **golden output** | The expected output for a given fixture, stored alongside it |
| **fixture version** | A content-addressed identifier for a fixture (SHA-256 of content) |
| **fixture inventory** | The record of all fixtures in `internal/testkit/fixtures/` |

---

## Fixture Locations

| Type | Path | Purpose |
|------|------|---------|
| Input fixtures | `internal/testkit/fixtures/` | Controlled test inputs |
| Golden outputs | `internal/testkit/golden/` | Expected outputs for regression tests |
| Integration source fixtures | `sources/` | Real source material (also used as integration fixtures) |
| Builder helpers | `internal/testkit/builders/` | Programmatic fixture construction for unit tests |

---

## Categories

### Category A — Real-file fixtures

Fixtures derived directly from real source documents in `sources/`. These are the highest-quality fixtures and must be used for integration and acceptance tests.

**Rules:**
- Must not be modified for test convenience. If the real file is invalid input, document it as such in a comment in the test.
- If the real file changes, tests that use it must be reviewed and updated.
- Golden outputs based on real-file fixtures must be regenerated and reviewed after any parser change.

### Category B — Synthetic fixtures

Fixtures constructed specifically for a test case. Used for unit and contract tests where a real file would be too noisy or unavailable.

**Rules:**
- Must include a comment in the fixture file or in the test explaining the scenario it represents.
- Must be representative of the real class of input it is standing in for.
- Must not omit properties that are structurally significant (e.g., do not omit a `phase:` field that the parser is required to handle).

### Category C — Builder-constructed fixtures

Fixtures constructed programmatically via `internal/testkit/builders/`. These are Go structs, not files.

**Rules:**
- Builders must produce structurally valid inputs by default.
- Builders must expose mutation helpers for testing edge cases (e.g., `WithMissingPhase()`, `WithDuplicateName()`).
- Builders must be reviewed when the domain model changes.

---

## Creation Rules

1. **Every new fixture must have a documented purpose.** A fixture with no explanation of why it exists is a maintenance liability.

2. **Fixtures must exercise a specific, named property.** Name the file to match: `risk_register_missing_phase.md`, not `test_fixture_42.md`.

3. **Fixtures must not be created by copying live production data unless the content is reviewed.** If content is sensitive, it must be anonymised before committing.

4. **Golden outputs must be generated by a deterministic command.** Manually-written golden files are permitted only for the initial version; subsequent versions must be generated.

5. **The command used to generate a golden file must be recorded** in a comment at the top of the golden file or in the test that uses it.

---

## Review Rules

1. **New fixtures must be reviewed before merging.** Reviewer must confirm: purpose is documented, content is representative, no sensitive data.

2. **Golden file updates must be reviewed as carefully as code changes.** A changed golden file means behaviour has changed. This must be intentional and documented.

3. **Fixtures for `mock-forbidden` layers must be real-file fixtures (Category A) or reviewed synthetic fixtures (Category B).** Category C builders are not sufficient for `mock-forbidden` layer tests.

---

## Versioning

Fixtures are versioned by content (SHA-256). When a fixture is updated:
1. The old SHA must be recorded in a comment or changelog if the change affects golden outputs.
2. Any test that references the fixture by content hash must be updated.
3. Any golden output derived from the fixture must be regenerated.

There is no formal fixture version number beyond the SHA-256 content address.

---

## Inventory

The fixture inventory is maintained informally: every fixture file must have a header comment explaining its purpose. A formal index (`internal/testkit/fixtures/INVENTORY.md`) is recommended once the fixture count exceeds 20.

---

## Prohibited Practices

| Practice | Why it is prohibited |
|----------|---------------------|
| Fixtures that always produce PASS | They test nothing. A fixture that never triggers a failure mode is not a fixture; it is dead code. |
| Anonymous fixtures (`fixture1.md`, `testdata.json`) | Reviewer cannot determine what property is being exercised |
| Generated fixtures committed without review | Unreviewed generated content is a backdoor for incorrect expected outputs |
| Fixtures with live credentials or PII | Security violation |
| Mutable fixtures shared across tests | Tests become order-dependent and non-reproducible |
